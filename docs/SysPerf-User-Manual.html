SysPerf User Manual

System Performance Agent — version 5.4.2

A self-improving performance dashboard for Windows 11. It measures the PC, explains what holds it back, and changes it only in ways it lists and you can undo.

#1. Introduction

#1.1 What SysPerf is

SysPerf watches how your Windows 11 machine is actually behaving, compares that against where it started and what it is capable of, and tells you what to change to make it faster.

It runs entirely on your machine as a small local web dashboard, plus a background sampler that reads Windows performance data every twenty seconds.

#1.2 What SysPerf is not

It is not an optimiser that changes settings for you. SysPerf reads. It never writes to the registry, never disables a service, never deletes a file, never changes a power plan. When it finds something worth fixing it tells you what it measured, why that matters, and what to do — and then you decide.

This is a deliberate design constraint rather than an unfinished feature. Tools that silently modify Windows are impossible to audit: when something breaks a week later, you cannot tell whether the tool did it. Because SysPerf only reads, uninstalling it leaves nothing to revert.

#1.3 Three ideas that make it different

Your machine sets the standard. On first run SysPerf records a baseline — the state of your machine right now — and derives its targets from your actual RAM, disk size and measured process floor. A 64 GB workstation and an 8 GB laptop get different targets because the same number cannot be correct for both. There are no constants copied from someone else's computer.

It admits what it cannot know. A measurement that needs more data reports measuring and is left out of the score rather than being assumed good. A fault that Windows itself reports as "OK" — a touchpad button that sticks, a fan that rattles — cannot be auto-detected at all, so there is a manual watchlist for it.

It scores the sustained state, not the moment. Process and connection counts fluctuate constantly. Scoring the latest reading would make the score collapse every time you opened a browser tab, so SysPerf scores a rolling median instead. The live gauges still show the raw value.

#1.4 Who it is for

Anyone who wants to know why their Windows machine feels slow and what to do about it: developers on heavy toolchains, analysts with large spreadsheets, anyone on a corporate laptop weighed down by management agents, and IT staff who need evidence rather than an impression.

#2. Requirements

Requirement Detail
Operating system Windows 11 (build 22000 or later). Windows 10 works but is not the test target.
PowerShell 5.1, which ships with Windows. PowerShell 7 also works.
Python 3.10 or later. The installer can fetch it via winget if it is missing.
Privileges Standard user. Nothing requires administrator rights.
Disk space About 60 MB including the private Python environment, plus up to 12 MB of history.
Network Needed once, to download two Python packages. After installation SysPerf works entirely offline.

Non-English installations of Windows are fully supported. SysPerf reads performance data from locale-independent system classes rather than from performance-counter names, which are translated, and identifies power plans by their unique identifier rather than by their display name.

#3. Installation

#3.1 The standard install

Unpack the SysPerf folder somewhere convenient, open PowerShell in it, and run:

powershell -ExecutionPolicy Bypass -File install.ps1

-ExecutionPolicy Bypass applies to that one command only. It does not change the machine's script policy.

The installer will:

  1. confirm your Windows and PowerShell versions;
  2. find Python 3.10+, offering to install it with winget if none is present;
  3. create a private virtual environment in %LOCALAPPDATA%\SysPerf\venv;
  4. copy the application to %LOCALAPPDATA%\SysPerf\app;
  5. write a starter configuration file;
  6. create Start Menu entries for the dashboard and for a one-off report;
  7. register a sign-in task so the dashboard is always running;
  8. start it and confirm it responds.

When it finishes, the dashboard is at http://127.0.0.1:5056/.

Everything is written to two places: %LOCALAPPDATA%\SysPerf and your own Start Menu folder. No Windows service is created, no shared location is touched, and no policy or system setting is changed.

#3.2 Installer options

Option Effect
-Port 5100 Serve on a different port. Use this if 5056 is taken.
-NoAutoStart Do not register the sign-in task. Start SysPerf yourself when you want it.
-NoStart Install without launching. 
powershell -ExecutionPolicy Bypass -File install.ps1 -Port 5100 -NoAutoStart

#3.3 Running without installing

To try SysPerf, or to get a report from a machine you would rather not install anything on:

powershell -ExecutionPolicy Bypass -File run.ps1 -Report   # one-off text report
powershell -ExecutionPolicy Bypass -File run.ps1           # dashboard

This creates a .venv folder inside the SysPerf directory and touches nothing else. Delete the folder to remove it completely.

#3.4 Installing with pip

py -m pip install --user .
sysperf --report
sysperf

Useful for scripted deployment. You will need to arrange autostart yourself.

#3.5 Running under WSL 2 (optional)

SysPerf can run inside a WSL 2 distribution and reach Windows through interop:

bash install-wsl.sh

Consider this only if you already run local services in WSL, or if you cannot install Python on the Windows side. The trade-offs: every sample pays the WSL-to-Windows interop cost of a second or two, and the dashboard is only up while WSL is running. In exchange, the WSL panel gains Linux-guest memory figures.

#3.5a Running in a container (optional, 3.2.0+)

On WSL 2 with Docker, the dashboard can run in a hardened container:

bash container/install-container.sh            # add --timer for the daily catalog refresh

The container has no capabilities, a read-only root filesystem and is published on 127.0.0.1 only. It cannot run Windows executables itself, so a host-exec broker (sysperf-hostexec.service, running as you) executes the PowerShell sample and remediations on its behalf. Only allowlisted programs run, -File scripts must live inside the distribution or the data directory, and every call is logged to container/broker/broker.log. Set allow_arbitrary_pwsh to false in container/broker/policy.json for a strictly read-only dashboard.

State is the same directory install-wsl.sh uses, so you can switch between the two without losing history. Full notes: container/README.md.

#3.6 If installation fails

"Python 3.10 or later is required and winget is unavailable." Install Python from https://www.python.org/downloads/windows/, ticking Add python.exe to PATH, then run the installer again.

"Python was installed but could not be located." The new PATH is not visible to the current console. Open a new PowerShell window and re-run the installer.

"Dependency installation failed." Usually a corporate proxy. Set it and retry:

$env:HTTPS_PROXY = 'http://proxy.example.com:8080'
powershell -ExecutionPolicy Bypass -File install.ps1

"Task Scheduler registration failed." Some managed machines block task creation. The installer detects this and falls back to a shortcut in your Startup folder, which achieves the same thing. No action needed.

#4. First run

#4.1 What happens in the first minute

The first sample is a fast one — memory, processes, handles, disk, CPU — so the dashboard has something to show within a few seconds.

The second sample is a full sweep: it additionally enumerates services, startup entries, network connections, hardware and drivers. That takes up to a minute on a busy machine, which is why it is not what you wait for on arrival. From it SysPerf writes baseline.json — your starting point — and derives the targets for every criterion.

Until the sweep finishes the dashboard says so, and shows live values without scores. Scores and recommendations appear as soon as the baseline exists. Afterwards the full sweep runs every fifteenth sample (about every five minutes).

#4.2 Why everything reads 0%

Because the baseline is the current state, no distance has been travelled yet. That is correct, not a bug. The numbers move when you act on the recommendations.

If you would rather measure from a machine you have already tuned, act on the recommendations first. Then delete baseline.json from the data directory (sysperf --where shows it) and restart SysPerf. The next settled stretch of samples becomes the new baseline.

#4.3 The first ten minutes

Two things need history before they can say anything useful:

  • the WSL memory trend, which needs at least six samples over ten minutes;
  • the adaptive layer, which needs about twenty samples before it stops saying "learning your pattern".

Leave the dashboard running and check back later.

#5. Reading the dashboard

The page is laid out top to bottom in order of usefulness: what to do, then how you are doing, then the evidence.

#5.0 Summary and Details tabs

Two tabs sit at the top-left, above the title.

  • Summary (default) is the whole dashboard distilled into a 10-category scorecard: memory pressure, WSL 2, browser footprint, application handles, CPU & processes, storage, network optimisation, Wi-Fi connectivity, hardware & drivers, and component currency. Each row shows a score out of 100 and the remaining room for improvement (100 − score), with one overall system score. Categories that cannot be evaluated yet show "measuring".
  • Details is the full dashboard: charts, scorecard, browser ownership, WSL, Wi-Fi, network optimisation, hardware, drivers and component upgrades.

The tab you last used is remembered. The overall score shown on the Details header is the same number as the Summary's overall score — both come from one computation, so they never disagree.

#5.0.1 Wi-Fi, network optimisation and component upgrades (new in 2.0)

  • Wi-Fi connection — SSID, negotiated link rate, radio generation, and band/channel. Signal strength, band, channel and Rx/Tx rates require Windows Location permission for the WLAN service (Settings → Privacy & security → Location). Without it SysPerf still reports the adapter-level link speed and tells you what to enable.
  • Band & channel overlap — scans neighbouring access points and recommends the clearest 2.4 GHz channel (only 1, 6 and 11 do not overlap) and the least used 5 GHz channel. Channel and width are access-point settings: SysPerf tells you what to change on the router, it cannot change them for you.
  • Network optimisation — the TCP connection footprint, active adapters and a prioritised fix plan. Each action is tagged client, router or windows so it is clear where it applies.
  • Component upgrades — a version-currency table for every catalogued component (Windows build, PowerShell 5.1/7, Edge, WebView2, graphics and network drivers, BIOS/UEFI, WSL and the tools inside the WSL distro, and SysPerf's own toolchain — every package in the CI SBOM), each with an estimated performance benefit. A component the machine does not have is listed last as not installed; it is never counted as an upgrade or in the total. latest is the vendor's newest public release, checked daily, with the reviewed catalog as the fallback — treat it as guidance, and confirm driver and firmware versions with your OEM's support tool.

#5.1 Header

Live machine facts — uptime, RAM, current CPU, process and service counts, samples collected, SysPerf version. The dot on the right is green when data is fresh, amber when the last sample is stale, red when the collector reported an error.

Hide descriptions collapses the long explanatory notes for a denser view. The setting is remembered. Recommendations are never hidden by it.

#5.2 Alerts

Only appears when something needs saying: a WSL memory ceiling under threat, a kernel pool well above your baseline, or a collector error.

#5.3 Overview cards

  • System score — the mean of the ten Summary categories; the same number the Summary tab shows. Categories still measuring are excluded rather than counted as good. Room for improvement is 100 − system score.
  • Room for improvement — the remaining distance to target.
  • Criteria status — how many are met, partial, regressed or measuring.
  • Memory pressure right now — commit charge against physical RAM. When commit charge exceeds RAM, compression and paging are on the hot path and everything feels slower.

#5.4 Recommendations

The actionable part of the tool. Each card gives:

  • a severity (critical, high, medium, low) and a category;
  • needs admin, when the fix requires elevation;
  • the finding — what was measured;
  • why it matters, in terms of what you experience;
  • numbered steps to take;
  • an optional command you can run yourself;
  • the expected effect.

Work top down. Severity reflects the size of the effect on responsiveness, not how easy the change is.

#5.5 Key metrics

Six headline gauges — commit charge, Memory Compression, available memory, WSL memory, browser processes, handles — each with its live value, its change against baseline, its target, and a sparkline. Baselines and targets come from the server, so they always agree with the scorecard.

#5.6 Self-improving scorecard

Your personal-best layer. For each tracked metric it shows the best daily typical you have ever recorded, a stretch target just beyond it, and today's typical. The bar only ever moves in the improving direction, so it tightens as your habits improve and never rewards a regression. A star marks a new personal best today.

#5.7 Success-criteria scorecard

One row per criterion: baseline, live value, target, change, progress bar, room remaining and status.

Status Meaning
met At or better than target.
partial Between baseline and target, or within the noise band.
regress Meaningfully worse than baseline (beyond the 2% dead-band).
measuring Not enough data yet. Excluded from the overall score.

The Live column is the raw latest reading; Progress is computed from the smoothed value. They can disagree briefly, and that is intentional — see section 6.

#5.8 Trends

Rolling history for memory, WSL memory, handles, kernel pools, browser processes, CPU, network connections and startup entries. Dashed lines mark targets. All charts are hand-drawn SVG: the page loads no external scripts and works offline.

#5.9 Browser processes

Usually the biggest single lever on an office machine, and the most misunderstood.

Windows runs two kinds of browser process: the browser you opened, and embedded browser processes (WebView2) started by other applications — file sync, Start menu search, chat clients, VPN portals. Task Manager shows them all as browser engines, but only some are yours to close.

  • Embedded browser by host application — which app owns each group.
  • Closability — mandatory (cannot be closed) versus in use versus discretionary, with the floor arithmetic. Anything above the realistic floor is discretionary: tabs and extensions you can close.
  • Edge composition — extension, renderer, utility and main processes, plus the memory extensions are holding. Extensions are the biggest lever, because one with a persistent background page never releases its process.

If an application of yours is being counted as discretionary when it should not be, add it to browser_hosts in the configuration — see section 8.4.

#5.10 WSL 2 and kernel pools

The WSL card only appears when WSL is present.

  • WSL 2 memory — the working set against the configured cap, whether a .wslconfig exists, and whether automatic reclaim is enabled.
  • Kernel pool versus baseline — memory allocated by drivers: antivirus and EDR filters, virtual disks, network filters. Applications cannot reach it, so closing programs will not reduce it. It is shown because unexplained pool growth is worth knowing about, not because you can fix it directly.
  • Disk and background churn — free space against target, svchost count, and Windows Search host processes. Search hosts at zero means the index is down and searches are scanning the disk.

#5.11 Hardware health

Device Manager fault codes, storage health, battery charge and wear against design capacity, and input devices. Plus your known-issue watchlist — see section 8.5.

#5.12 Drivers health

Third-party driver inventory, unsigned packages, packages older than four years, and driver-specific fault codes. Stale storage, chipset, graphics and network drivers are the ones that measurably affect performance; a stale driver for a printer you no longer own does not matter.

#5.6 Auto-Improve tab

The fourth tab is the autonomous loop's own view. Six blocks, top to bottom:

  • Status chips — current score against the threshold, the standing mode, the scan cadence and time to the next scan, cycles completed, the current usage load, the long-term score trend, how many days of history exist, and which risk classes may run unattended.
  • Controls — switch mode (auto / observe / off), Scan & analyse now, and Scan, RCA & fix now. Both buttons are CSRF-protected; the mode you choose persists across restarts.
  • Root-cause analysis — one row per criterion that is under target, ordered by its share of the scoring gap. Each row shows the sustained value, the target, that share, the attributed cause with a confidence, the reasoning (including the long-term direction and how many days the criterion was met), and the remediation that maps to it. Evidence from the same sample sits under the criterion name, so a handle count is shown next to the process count that explains it.
  • Last cycle — what was applied, what was deliberately not applied and why, and — once the next scan has landed — the measured before/after of every metric the action targeted.
  • Long-term usage trends — the daily typical of each criterion over the trend window, with its drift in percent per day, direction, how many settled days it was met, and a plain verdict.
  • Learned fix effectiveness and Open proposals — the ledger of what actually worked, and the structural changes left for a human.

A row with no remediation is not an oversight: browser process count and CPU utilisation are yours to change, and the dashboard says so rather than pretending a cache flush would help.

#6. How scoring works

#6.1 Progress

For each criterion:

progress = (current − baseline) ÷ (target − baseline)     clamped to 0–100

Reaching the target always scores 100%, even in the unusual case where your starting value was already better than the achievable floor.

#6.2 Where targets come from

Targets are derived once, when the baseline is captured, from your machine's own capacity. The exact fractions are configurable; the defaults are:

Criterion Target
Commit charge The lower of 75% of RAM, or 15% better than baseline
Memory Compression The lower of 5% of RAM, or half of baseline
Available memory The higher of 30% of RAM, or 25% better than baseline
Total handles 15% better than baseline
WSL 2 memory The .wslconfig cap, or 35% of RAM if there is none
Browser processes The measured floor plus a little headroom
System volume free The higher of 15% of the volume, or 10% better than baseline
Remote connections The higher of 25, or 30% fewer than baseline
Startup programs The lower of 10, or 45% fewer than baseline
Hardware faults Zero

Every target is then clamped so it is an improvement on your baseline but never below a physical floor. That clamping is what stops a criterion from being permanently red for reasons you cannot influence — asking for fewer browser processes than the non-closable ones your employer's software requires, for instance.

#6.3 Smoothing

Counts breathe. Opening a document, a background sync, an antivirus scan — each moves process, handle and connection counts for a few seconds. Scoring the latest sample would make the score collapse and recover constantly and mean nothing.

So the score uses the median of the last fifteen samples (about five minutes). A genuine, sustained change moves the median within one window; a spike does not move it at all. Live gauges and charts still show the raw value.

Two metrics are both bursty and sampled sparsely, so they get a longer window: remote TCP connections use sixty minutes, because sync and scan activity can triple the count for several minutes before it settles.

#6.4 The noise dead-band

A row is regress when its smoothed value is worse than the baseline and has not reached the target. Smoothing (below) is what keeps one noisy sample from flipping it.

#6.5 Ceiling criteria

WSL memory is not a reduction target. It is a ceiling: at or below the cap and not growing. The generic formula does not apply, because the cap normally sits above the starting value, so improving would score negative.

Instead it is scored on being under the cap and not trending toward it, with three guards:

  • A minimum window. Windows trims working sets opportunistically. A multi-gigabyte trim over four minutes extrapolates to a meaningless five-figure rate, so at least six samples over ten minutes are required.
  • Re-anchoring. If the VM restarts, or the working set collapses from a high steady state, the window restarts. Otherwise the recovery ramp afterwards would read as a leak.
  • Runway, not slope. A slow rise from a low base is normal churn. The criterion only complains when the cap is genuinely threatened — close to it, or projected to reach it within a few hours.

Until the window is long enough the criterion reads measuring and is left out of the overall score. The dashboard says "n of m criteria scored" so you can see that it abstained rather than assumed.

#6.6 Adaptive scoring

The plan scorecard answers "how far through the plan am I". The adaptive layer answers a different and often more useful question: "is today better than my normal".

For each behaviour-driven metric it tracks:

  • personal best — your best daily typical, so one lucky reading right after a reboot does not set an unreachable bar;
  • adaptive target — 5% beyond that best, always in the improving direction;
  • adaptive baseline — your worst daily typical;
  • today's typical — the mean of today's samples.

Structural metrics — disk free space, startup entries, hardware faults — are deliberately excluded. Adapting them would add noise, not signal.

#7. Recommendations reference

Twenty rules. Each fires only when the evidence is present, because a dashboard of unconditional advice trains people to ignore it.

#7.1 Memory

Recommendation Fires when
Commit charge exceeds physical RAM Commitments are larger than RAM, so compression or paging must satisfy them. Critical above 85% of the commit limit.
Memory Compression is holding a large working set The compression store exceeds 4% of RAM. It only grows when RAM is oversubscribed, and every hit costs CPU to decompress.
Available physical memory is low Below 15% of RAM. Below roughly 10% the memory manager spends its time reclaiming instead of serving.
A single process dominates memory use One application holds more than 12% of RAM. Usually the cheapest fix available: restart that one app.

#7.2 Startup and maintenance

Recommendation Fires when
Too many programs start automatically Enabled auto-start entries exceed target. Lists the actual entries. Disabling is reversible and does not uninstall anything.
The machine has not been restarted in a long time Uptime over seven days. A restart clears leaked handles, pool growth and pending updates.
A restart is pending Windows has set a reboot flag from servicing. Until you restart, components run in a mixed state.
Open handle count is above your baseline A steady climb that never falls back points at a process that opens resources without releasing them.

#7.3 Browser

Recommendation Fires when
Browser-engine processes are above target Above the floor-derived target. Names the resident extension processes and how much memory they hold, since extensions are the biggest lever.

#7.4 Storage

Recommendation Fires when
System volume is running out of free space Below 15% free; critical below 7%. Windows needs free space for the pagefile, servicing, temp files and the search index.
Pagefile usage has approached its allocated size Peak usage within 20% of the allocation. With a fixed-size pagefile the next spike fails outright and applications crash.

#7.5 Network

Recommendation Fires when
More background network connections than necessary Remote connections above target. Includes a command that groups connections by owning process so you can see who is talking.

#7.6 Drivers and hardware

Recommendation Fires when
Devices are reporting driver fault codes Any device with a driver-specific Device Manager error. Graphics, storage and network fallbacks are a common cause of unexplained slowness.
Third-party drivers older than four years are installed Old drivers miss later power-management and stability fixes. Prioritise storage, chipset, graphics and network.
Hardware faults detected Device Manager errors or a disk not reporting Healthy. An unhealthy disk is a data-loss risk before it is a performance problem.
Battery capacity has degraded significantly Full-charge capacity below 70% of design. Firmware caps processor power on a worn battery, which reads as sudden slowness when unplugged.

#7.7 Power and platform

Recommendation Fires when
A power-saving plan is active Power saver caps processor frequency and delays turbo — the most common cause of a machine that is slow for no visible reason.
Real-time protection is reported as disabled Reported for completeness, not as a performance tip. Never disable protection to gain performance.
Windows Search is not running With the index down, searches fall back to scanning the filesystem.

#7.8 WSL 2

Recommendation Fires when
WSL 2 is running without a memory cap No .wslconfig exists. WSL may claim up to half of RAM and not return it. Includes a ready-made file sized for your machine.
Automatic memory reclaim is not enabled .wslconfig exists without autoMemoryReclaim, so a single build can hold gigabytes for the rest of the day.

#8. Configuration

#8.1 Where the file is

sysperf --where

Typically %LOCALAPPDATA%\SysPerf\sysperf.config.json. Every key is optional; anything omitted keeps its default. Restart SysPerf after editing. sysperf.config.example.json in the source folder is a fully annotated copy.

#8.2 Server and sampling

Key Default Meaning
host 127.0.0.1 Bind address. Loopback only: there is no authentication (see section 9).
port 5056 Listening port.
allowed_hosts [] Extra Host names SysPerf answers to, for example one a local reverse proxy forwards. Any other Host gets 403.
open_browser false Open the dashboard on start.
sample_seconds 60 Fast-tier cadence, clamped to 30–600. The slow tier runs every 5th sample.
collector.persistent_shell true Reuse one PowerShell process for every sample.
history.raw_days 14 Days of raw samples kept in SQLite (1–90). Hourly summaries are kept for 400 days.
version_check true Read public release feeds once a day for the Components view.

#8.3 Targets

Key Default Meaning
targets.* see table in 6.2 Fractions of your capacity used to derive targets. Raise to loosen, lower to tighten.
wifi.plan_mbps {} Your SSID and the speed you pay for, e.g. {"MyHome": 100}.

Editing targets only affects newly derived targets. To apply changes to an existing baseline, delete baseline.json from the data directory and restart.

#8.4 Browser ownership

The setting most worth editing. It tells SysPerf which applications' embedded browser processes you cannot close:

{
  "browser_hosts": {
    "mandatory": {
      "OneDrive": "File sync",
      "SearchHost": "Windows Start / Search",

Windows cannot detect a fault it does not consider a fault. Record those yourself in hw_watchlist.json in the data directory:

[

    "severity": "minor",
    "status": "open",

severity is critical, major, minor or low. Set status to resolved to keep the record without counting it as open. The file is re-read on every request, so edits appear immediately.

#8.6 Fixes and autonomous improvement

{

  "autoimprove": {
    "mode": "auto", "interval_seconds": 300, "threshold": 80,
    "allow_caution": false, "max_actions": 2,
    "cooldown_seconds": 1800, "settle_seconds": 120

Nothing that changes the PC runs (fixes, Explorer watchdog, tray auto-quit, OneDrive control), but everything is still detected and previewed. autoimprove governs the loop itself (see chapter 14). mode is the initial mode, because the value chosen in the dashboard is persisted. #9. Privacy and security

#9.1 What leaves your machine

Two things, and only what they need. The daily version check reads public release feeds: GitHub (including the winget index), PyPI, npm, Ubuntu, Microsoft Edge and endoflife.date. It sends nothing about your PC; turn it off with version_check: false. If you enable AI self-evolution, source excerpts and metrics go to the model provider you configure. There is no telemetry and no account, and the dashboard loads no third-party scripts, fonts or images.

#9.2 What it reads, and what it changes

The collector (src\sysperf\collect_win.ps1) only queries: Get-CimInstance, Get-Process, Get-ItemProperty, pnputil /enum-drivers, powercfg /getactivescheme. You are encouraged to read it.

SysPerf can also change the PC, but only through features that each have a switch and say how to undo them. In the Store build they are listed on Home → Optional features. In a scripted install they are on the App Control, Auto-Improve and AI Self-Evolution tabs:

  • automatic fixes: flush DNS, trim idle apps' working sets, clear standby memory;
  • the Explorer watchdog;
  • tray auto-quit, which asks first for each app;
  • the OneDrive lock policy;
  • App Control.

Autonomy starts at Observe. In the Store build every one of these starts off. fixes.enabled: false turns them all off. Its own state lives in its data directory.

#9.3 Treat the API as sensitive

/api/metrics describes your machine in detail: running process names, top memory consumers, installed drivers, enabled startup entries, connection counts, hostname and model. Wi-Fi SSID and BSSID are masked. That is still a useful reconnaissance picture, which is why the server binds to loopback only.

#9.4 How it is protected

  • Host and Origin checks. A request whose Host is not SysPerf's, and a POST from another origin, get 403. This stops a malicious page that rebinds its domain to 127.0.0.1 (DNS rebinding).
  • CSRF token. Every one of the 28 POST routes requires a per-process token.
  • Content-Security-Policy. Only this origin may load scripts, styles or images, or be fetched.
  • Secrets. The model API key is DPAPI-encrypted on Windows and never logged or returned.

There is no authentication and no TLS, so exposing SysPerf on a network is not supported.

#9.5 Sharing screenshots

The numbers alone identify little, but process and device names do. Crop or blur the Processes and Hardware panels before sharing. SSID and BSSID are already masked in the API.

#9.6 Reporting a vulnerability

See SECURITY.md. Please use a private security advisory rather than a public issue.

#9.9 Where is it running, and where is my data?

SysPerf measures a Windows host and can run natively on Windows, inside WSL 2, or (uselessly, but without crashing) on plain Linux. The tools and paths differ, so when anything looks wrong the first command to run is:

sysperf --where

It prints the detected platform, the PowerShell it resolved, whether collection is possible and why not if it is not, the code and data directories, the settings file in effect, the bind address and the remediation policy. /api/health reports the same facts as JSON.

Data never lives inside the installed package — once pip-installed that is site-packages, which may be read-only and is wiped on upgrade. The location is, in order: SYSPERF_DATA_DIR; else the directory an existing installation already uses, so upgrading never orphans your history; else %LOCALAPPDATA%\SysPerf\data on Windows or $XDG_DATA_HOME/sysperf (default ~/.local/share/sysperf) elsewhere.

If sysperf --where reports can collect: no, the dashboard has no Windows host to query. Inside WSL, enable interop in /etc/wsl.conf and make sure C: is mounted; anywhere else, point SYSPERF_PS_EXE at pwsh.exe or powershell.exe.

#9.10 Keeping the component catalog current

The Components view compares each measured version against a latest target from components.json. refresh_components.py re-assesses those targets from each component's supported channel (apt, PyPI, nodejs.org, GitHub releases for PowerShell) and stamps the assessment date. It is the only part of SysPerf that makes outbound requests, and it runs only if you schedule it — install-container.sh --timer installs a daily systemd timer. SYSPERF_COMPONENTS_DIR chooses which components.json it updates.

#12. Troubleshooting

The dashboard does not load.

Get-ScheduledTask -TaskName 'SysPerf Dashboard'
& "$env:LOCALAPPDATA\SysPerf\sysperf.cmd"     # run in the foreground to see errors

"collector produced no output". PowerShell could not run the collector. Try it directly — the error it prints is the real cause:

powershell -NoProfile -ExecutionPolicy Bypass `
  -File "$env:LOCALAPPDATA\SysPerf\app\src\sysperf\collect_win.ps1" -Full

Everything reads 0%. Expected on the first day. See section 4.2.

Progress looks worse than the live value. Progress is computed from the smoothed value, not the latest sample. See section 6.3.

A criterion is stuck on "measuring". The WSL trend needs six samples over ten minutes. Leave it running.

Samples take several seconds. The full sweep (every fifth sample) enumerates services and drivers. Raise sample_seconds to sample less often.

A target looks unreachable. Check whether the criterion is bounded by a physical floor — the browser panel shows its floor arithmetic explicitly. If a mandated corporate application is being counted as discretionary, add it to browser_hosts (section 8.4). Otherwise loosen the relevant fraction under targets, delete baseline.json and restart.

Port already in use. Reinstall with -Port 5100, or set port in the config file and restart.

Battery wear shows nothing. Design and full-charge capacity come from a WMI namespace some firmware does not expose. Charge and status still work.

High CPU from SysPerf itself. The sampler should be idle between samples. If it is not, run with --verbose and check for a collector that is timing out and retrying; raising sample_seconds is the quick mitigation.

#13. Frequently asked questions

Does SysPerf slow my machine down? A fast sample is a few hundred milliseconds of PowerShell every twenty seconds. The full sweep costs a few seconds every fifteenth sample. The API caches its snapshot, so an open dashboard is nearly free.

Why does it not just fix things? Because then you would not know what changed. Silent registry and service edits are exactly why "optimiser" tools have the reputation they do. Recommendations tell you what to do, what it affects, and whether it can be undone.

Can I trust the recommendations? Each one states what it measured, so you can check the reasoning rather than take it on faith. None of them are secret tweaks: they are the changes a competent administrator would make, driven by measurements from your machine.

Will it work on a managed corporate laptop? Yes — that is a design target. No elevation is needed, and if policy blocks scheduled-task creation the installer falls back to your Startup folder. Note that some recommendations, such as disabling a security agent's startup entry, are not yours to act on; SysPerf says so where it can.

Why is my browser-process target so high? Because it is derived from what your machine actually requires. If file sync, Start menu search, a VPN client and a chat app each run embedded browser processes, the floor is genuinely high and pretending otherwise would just make the row permanently red.

Can I run it on several machines? Yes, independently. There is no aggregation layer, but the JSON API is stable enough to scrape into one if you want to build it.

Does the dashboard need to be open? No. Collection happens in the background service; the dashboard is only a view of it. sysperf --report needs no browser.

How much disk does the history use? Up to about 12 MB, trimmed automatically.

Can I delete the history and start over? Yes. Stop SysPerf, delete history.jsonl, baseline.json and adaptive_state.json from the data directory, and start it again.

#14. Autonomous improvement

SysPerf can close its own loop. Every five minutes it scans, and when the overall score is below the threshold it works out why and applies the remediations that address the cause — then measures whether that actually helped and remembers the answer.

Nothing in this chapter changes how the machine is measured, and nothing here can run a disruptive fix. It is the Common-Fix engine (chapter 7) driven by evidence instead of by a human clicking.

#14.1 The cycle

  1. Scan — take a snapshot and fold it into the long-term record (trends_daily.json): per-criterion daily rollups, an hour-of-day usage profile, and the overall score per day, retained for six months.
  2. Judge — compare the score to autoimprove.threshold (80% by default).
  3. Diagnose — rank every criterion under target by its share of the scoring gap, then attribute a cause using both the short horizon (rolling median against target) and the long one (drift of the daily typical, chronic misses, current usage load).
  4. Act — apply the remediations that address those causes, subject to every guard in 14.4.
  5. Verify — on the next scan, measure what changed for the metrics the action targeted and record it.
  6. Learn — after three verified attempts with no net benefit, stop choosing that fix for that metric and say so.

#14.2 Why the cause matters

The same low number means different things, and the response differs:

Cause What the evidence shows Response
transient_spike worse than its own recent daily typical while the long-term trend is flat or improving a burst (sync, scan, build) — cheap reclaim at most
usage_driven machine load above its own norm, metric inside its usual band the measured cost of the work; not a fault
long_term_regression daily typical drifting the wrong way for days remediate, and escalate if the fix is proven useless
chronic_unreachable never met across five or more settled days the target is the problem — a retune is proposed, no fix is attempted
near_target within 5% of target nothing worth its disruption
steady_shortfall stable gap under normal load needs a structural change, not a reclaim

Two of these deliberately produce no action. Chasing a target that sits below the machine's floor is how a dashboard trains you to ignore it.

#14.3 What the long horizon adds

The multi-week record is not decoration; four behaviours depend on it:

  • Cause attribution — distinguishing a burst from a real regression requires knowing what a normal day looks like for this machine.
  • Preventive action — a criterion that is met today but has drifted the wrong way for days is remediated before the score breaches, with a projection of how many days remain.
  • Escalation — a long-term regression whose only safe remediation has been measured ineffective becomes a proposal for a human instead of a fix repeated forever.
  • Peak-hour awareness — user-visible fixes are held back during the hours the hourly profile shows as this machine's busiest.

On first run the store is seeded from the adaptive layer's own per-day aggregates, so the long view is available immediately rather than a fortnight later.

#14.4 Guards

  • Mode — off (scan, trend and RCA only), observe (also plan, execute nothing), auto (execute). Settable live from the dashboard and persisted.
  • Risk — only safe fixes run unattended. caution fixes require autoimprove.allow_caution and are additionally deferred out of peak hours. manual and session-killing fixes are never executed, in any mode.
  • fixes.enabled — with fixes off, the loop is a pure analyst.
  • Budget — at most max_actions per cycle (plus one when the long-term score trend is declining), and each action has a 30-minute cooldown.
  • Learned suppression — an action with no measured benefit over three verified attempts is skipped, with the reason shown.
  • No self-modification — the loop never edits targets, criteria or scoring. Structural changes are written to autoimprove_state.json as proposals.

#14.5 State files

File Contents
trends_daily.json daily and hourly rollups per criterion, plus the score per day
autoimprove_state.json mode, cooldowns, the effectiveness ledger, open proposals, last cycle
autoimprove_log.jsonl one record per cycle, capped at 500 lines
evolve_state.json the evolution generation, candidate recipes, generated shards, learned pairings, clusters, proposals and audit log
evolutions/*.md the rule documents the evolution layer has generated
actions_state.json which action items you have recorded as done, and when

All three live in the data directory (chapter 8.1) and contain only numbers and criterion names.

#14.6 Turning it off

Set autoimprove.enabled to false, or choose off in the dashboard, or simply leave fixes.enabled at its default of false — then the loop still explains the score and the trend, but never touches the machine.

#14.7 What it has learned

The loop scores a (fix, metric) pair, not a fix. The same action can help one criterion and do nothing for another, and conflating the two is how a dashboard ends up recommending something that has never worked.

For each pair the Auto-Improve tab shows the number of attempts, an exponential moving average of the measured normalised change, a win/loss count where the outcome was decisive, and a verdict:

Not every criterion can be closed automatically. A remediation that needs administrator rights cannot run, because the service is unprivileged by design — those appear as action items with the exact command instead. Two remediations added in 3.0.0 deliberately avoid elevation and so cover the metrics that previously had nothing: background_cpu_hog (CPU, run queue, disk) and trim_working_sets (commit, available memory, compression). Both refuse to touch kernel or VM pseudo-processes, security agents, or the shell taking the measurement.

Verdict Meaning
effective the measured average is positive — the loop prefers it
learning too few measurements to say
suppressed three or more measured attempts produced no gain, so the loop has stopped choosing it

Alongside that: learning events per day, a breakdown of what the cycles were spent doing, a newest-first feed of what each substantive cycle actually taught (including the before/after numbers), and per-metric knowledge sets showing the long-term shape of each criterion and which remediations are mapped to it. A criterion is learned, observed, mapped or unmapped; the last means nothing in the catalogue addresses it, so a shortfall there can only be escalated.

The tab also audits the loop against its own seven operating rules — unattended risk class, per-cycle action budget, cooldown, measure-before-repeat, the suppression threshold, manual actions never executed, and the bounded cycle log — over the retained window, and reports a violation rather than asserting compliance.

#14.8 What it needs you to do

Anything the loop may not do itself becomes an action item, with ordered steps, the exact command, how to confirm it worked, what should change, and any caveat worth knowing first. Each states specifically why automation is barred:

Reason Why it cannot be automated
Needs administrator rights the service runs unprivileged by design; only you can answer a UAC prompt
Would terminate this dashboard the action restarts the WSL VM that hosts the collector mid-measurement
Requires knowing what matters to you which start-up items or add-ins are essential is specific to how you work
No safe scriptable equivalent the setting lives behind a GUI or a per-application profile
Changes persistent configuration it keeps applying long after the shortfall has gone, so you should know
Target below what this machine delivers every available remediation has been measured and none closes it — a decision, not an action
Only you may grant new capability an evolution-generated candidate is inert until you accept it
Missing a measured value a recipe parameter has no evidence yet; inventing one would be worse

Items are open until either you press I did this — recorded as action taken, with your note and a timestamp — or the evidence closes them (resolved automatically). Every item has a stable identity, so the same work is never listed twice however many sources mention it, and an item you closed reopens itself, flagged recurred, if its trigger is raised again.

#14.9 What it wants to become

Every eight cycles an evolution pass turns accumulated evidence into capability the loop was not shipped with:

Kind Trigger Applied
learned pairing a fix measurably improved a metric it was not mapped to, twice automatically
candidate remediation a metric fell short eight times with nothing mapped to it only when you promote it
knowledge shard a metric accumulated eight shortfalls and has no rules automatically
cause cluster verification outcomes show which family of fix resolves which cause automatically
structural proposal the target is unreachable, so no action can help human decision

It cannot write commands. A candidate is always a parameterised entry from a fixed, reviewed recipe library, filled in from measured evidence — never composed from log content or model output. A candidate is inert; promoting it registers the recipe as a manual recommendation carrying the exact command, which the loop surfaces in the root-cause analysis and then skips. Giving a recipe a command the loop can execute is a deliberate change to the source.

Hard caps bound each pass and each registry. Writes go only to evolve_state.json and evolutions/ — the program's own modules are never modified — and every evolution records the files and registry keys it created, so Roll back the last evolution fully reverses it.

#14.10 Its own tests

The tab shows this project's eight quality gates as last run, and can run them:

Gate Checks
discover every module is registered with the coverage gate, so none can dodge it
compile every module byte-compiles and carries a docstring
lint AST checks: dead imports, bare except, mutable defaults, stray prints
unit the pytest suite
coverage 100% line coverage on every module
frontend the page's JavaScript parses, every element id it reads exists, and every interpolation of a server-provided string is escaped
browser a real Chromium drives every tab, detail section and control; tests/uicov.py requires 100% of the interface to be exercised
live the running service: status codes, security headers, JSON contracts, CSRF enforcement, GET purity, bounded state files

The browser gate is what stops the others being complacent about the page: a static check can prove the JavaScript parses, but only a browser can prove a panel renders. It is skipped cleanly when Playwright is not installed, so the suite stays green on a machine without browsers.

A result older than six hours is reported as stale rather than presented as current. If your installation does not ship the gate runner the card says so instead of offering a button that cannot work.

#14a. AI self-evolution and autonomy levels (4.0)

The AI Self-Evolution tab controls everything that acts on its own.

Autonomy level:

  • off — nothing autonomous;
  • observe — the default: recommend only;
  • safe_auto — runs only the low-risk, reversible actions you tick;
  • self_evolve — additionally runs source-code evolution cycles.

What the tab shows:

  • the current evolution state, and the last and next attempt;
  • candidate counts, AI usage and estimated cost;
  • every attempt with its trigger, problem, model, proposal, files, test, security and benchmark results and final decision;
  • the diff of any candidate, with Approve/Reject;
  • the measured before/after effect of every unattended action.

What evolution needs: a git checkout of the source, an evo_bench.py defining benchmarks, an AI provider, and an isolation backend (bubblewrap on Linux/WSL, or Docker). If something is missing, the tab says exactly what.

Approving a candidate records your decision and shows the git merge command. SysPerf never merges or deploys a change itself.

The configuration reference, security architecture and Windows validation steps are in docs/AI_EVOLUTION.md.

#A.2 Sampling tiers

Two tiers keep the cost low. The fast tier runs every sample_seconds (default 60 s) and gathers memory, CPU, process and Wi-Fi link data. The slow tier (-Full) runs every 5th sample (≈ 5 min) and adds services, startup entries, network, hardware, drivers, component versions and the Wi-Fi neighbour scan.

Slow-tier values are carried forward between full sweeps (see CARRY_FORWARD_KEYS) so the dashboard shows the last known value instead of a gap. The first sample is deliberately fast so the dashboard is not blank while a full sweep runs; the second sample is full, which is when the baseline is captured.

#B.3 Deliberate collection choices

  • Locale independence. Performance data comes from Win32_PerfFormattedData_* CIM classes rather than Get-Counter, whose counter paths are localised and fail on non-English Windows.
  • No assumed drive letter. The system volume is read from %SystemDrive%.
  • Power plans by GUID. Display names are localised and cannot be matched reliably.
  • Driver inventory via pnputil /enum-drivers. Win32_PnPSignedDriver is the obvious alternative and is slow enough to time the sample out.
  • Environment-based program paths. Edge and PowerShell 7 are located through %ProgramFiles%, %ProgramFiles(x86)%, %ProgramW6432% and %LOCALAPPDATA% with a registry fallback, so a non-C: Windows install works.
  • PowerShell 5.1 compatible. The collector avoids PS7-only syntax, so it runs on a stock Windows 11 machine; PowerShell 7 is used automatically when present.

#Appendix C. Scoring mathematics

#C.1 Criterion progress

For a normal criterion, progress is the fraction of the baseline → target journey completed, clamped to 0–100:

progress = clamp( (current − baseline) / (target − baseline) × 100 , 0 , 100 )

If the target is met, progress is forced to 100 — otherwise a metric that was already better than its achievable floor at baseline time would report "met" alongside 0 %.

Smoothing. Counts breathe constantly, so the sustained value is scored: the rolling median of the last 5 samples (≈ 5 min at the 60 s cadence). Remote connections, which burst, use a 60-minute window. Carry-forward metrics use the raw latest value, because a short median would only return a stale earlier step. Live gauges and charts always show the raw latest value.

Session boundary. Samples from before a collector gap longer than the gap threshold (a reboot or sleep) are left out of the median, so a stale pre-reboot value cannot hold a row at "regress".

#C.2 Ceiling criteria (WSL memory)

"At or below the cap and not growing" cannot use the formula above, because a cap normally sits above the starting value. Instead the working-set slope is estimated by least squares over the last window_seconds, and the score is based on remaining runway:

  • above the cap → 0, regress;
  • insufficient samples or span → measuring (excluded from the overall);
  • flat or falling → 100, met;
  • rising with ≥ 12 h of headroom and under half the cap → 100, met (churn, not a leak);
  • rising with ≥ 3 h of headroom → 50–95, partial;
  • otherwise → regress.

The window is re-anchored at a genuine VM restart or working-set reset (detected as a collector gap or a collapse from a high steady state) so the recovery ramp afterwards does not read as a leak.

#C.3 Target derivation

Targets are ratios of the machine's own capacity, never absolute constants (see config["targets"]), then clamped so a target is always an improvement on the baseline and never crosses a physical floor. Examples: commit charge ≤ 75 % of RAM, available ≥ 30 % of RAM, free space ≥ 15 % of the volume, browser processes ≥ the measured non-closable floor plus headroom.

#C.4 The 10-category Summary score

The Summary distils everything into ten categories scored 0–100. Categories that map to a criterion use that criterion's progress; the rest are computed from live values. Room for improvement is 100 − score.

Category How it is scored
Memory pressure Mean progress of commit, compression and available memory
WSL 2 The vmmem ceiling score, or headroom against the configured cap
Browser footprint Browser-process criterion progress
Application handles Handle criterion progress
CPU & processes 100 − CPU%, less a penalty when the run queue is non-zero
Storage Mean of free-space progress and disk health
Network optimisation Mean of remote-TCP and startup-entry progress, less a penalty for channel overlap
Wi-Fi connectivity Signal percentage, or a band from the negotiated link rate when Location is denied
Hardware & drivers 100 less penalties for device faults, driver faults, stale drivers and unhealthy disks

The overall score is the mean of the categories that could be evaluated; measuring categories are excluded rather than assumed good. The Details header and the Summary tab display the same overall number — both call one shared computation, so they cannot disagree.

#C.5 Adaptive (personal-best) layer

Independently of the fixed criteria, SysPerf tracks the best value you have actually achieved per metric and sets a stretch goal slightly beyond it (adaptive.stretch, default 5 %). It reports today's typical value, whether you are at or beat your personal best, and a self-improvement percentage. It needs adaptive.learn_samples observations before it will score a metric.

#Appendix D. Wi-Fi and network analysis internals

#D.1 Why two data sources

Get-NetAdapter and Get-NetConnectionProfile work without elevation or any privacy permission, and yield the SSID, negotiated link rate, adapter model, network category and IPv4 connectivity. The richer detail — signal percentage, band, channel, Rx/Tx rates and the neighbour scan — comes from netsh wlan, which on Windows 11 is gated behind Location permission for the WLAN service and may also require elevation.

When netsh is unavailable SysPerf sets detail_limited and the dashboard shows adapter-level data plus an explanation of what to enable. It never reports a fabricated signal value.

#D.2 Channel overlap model

  • 2.4 GHz — 20 MHz channels are spaced 5 MHz apart, so two access points overlap when their channel numbers differ by less than 5. Only 1, 6 and 11 are mutually non-overlapping. Each candidate is scored by signal-weighted neighbour load, and the clearest is recommended.
  • 5 / 6 GHz — 20 MHz channels do not overlap, so congestion is simply the co-channel count; the least-used common channel is recommended.

#D.3 Why SysPerf cannot "fix" overlap

Channel and channel width are access-point settings. A client can only choose which band to prefer and which access point to join. The optimisation plan therefore tags every action by where it applies — client, router or windows — and SysPerf changes none of them.

#Appendix G. Extending SysPerf

  • Retune thresholds — edit sysperf.config.json; nothing needs recompiling.
  • Adjust browser ownership — add host process names under browser_hosts.mandatory / in_use so the closability floor matches your environment.
  • Change the component targets — edit components.json. A component the machine lacks shows as not installed and is not counted, so adding an entry is safe.
  • Add a criterion — add a row to config.CRITERIA, derive its target in machine_profile.targets_for, and collect the field in collect_win.ps1. The scorecard, KPI cards and category score pick it up automatically.
  • Add a fix — add a detector and remediation in fixes.py, and register it in optactions.py with its risk, reversibility and rollback, so autonomy levels govern it.
  • Run the tests — python -m pytest from the project root.
